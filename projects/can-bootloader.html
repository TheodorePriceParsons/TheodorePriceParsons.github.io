Multi-Node CAN Bootloader

A custom bootloader to flash several STM32s at once over a CAN bus, no debugger needed. Updates over UART work end to end and CAN is validated in loopback; the two-board CAN bus is next.

How it works

Goal

Flash multiple STM32 boards at the same time over a shared CAN bus instead of plugging a debugger into each one. The drivers are written at register level wherever possible.

Progress

  • Done: two-project setup (bootloader + app), linker scripts, vector-table handoff to the app.
  • Done: register-level flash driver (sector erase, 32-bit programming, cache flush) and CRC-32 matching Python's zlib.crc32.
  • Done: UART update protocol and Python host tool; a 9.5 KB app installs in about 1 s.
  • Done: CAN1 at 500 kbit/s validated in loopback.
  • Next: carry the same protocol over CAN with two boards and transceivers, then broadcast to several nodes.

Boot decision

At reset the bootloader reads the header and the app's vector table. It jumps only if the magic number is present, the size is sane, the initial stack pointer lands in RAM and the CRC-32 of the whole image matches. Otherwise it stays and waits for an update. Holding the user button at reset forces update mode.

The jump disables interrupts, resets the clocks and peripherals, stops SysTick, clears every NVIC enable and pending bit, loads the app's stack pointer into MSP and branches to its Reset_Handler. The app then points SCB->VTOR at 0x0800C000 and re-enables interrupts.

Update protocol

  • SYNC: host and board agree they are talking.
  • START (size, CRC, version): erase the header first, then the app sectors. From this moment the old app is invalid.
  • DATA (offset, length, 256 bytes, chunk CRC): check the chunk CRC, program it, read it back from flash. A repeated chunk (lost ACK) is acknowledged without rewriting; a gap is rejected.
  • END: CRC-32 over the whole image in flash, then write version, size and CRC, and the magic number last, then reset into the app.

A power cut at any point leaves no valid magic, so the board never boots a half-written image.

CAN loopback

bxCAN at 45 MHz APB1: prescaler 5, 1 + 15 + 2 time quanta per bit, so 45 MHz / (5 × 18) = 500 kbit/s with the sample point at 16/18 = 88.9 %. The clock comes from the 8 MHz HSE rather than the internal RC, since CAN needs about 0.36 % accuracy here and the HSI is only ±1 %.

The first runs failed to start. Decoding the status registers found the cause: BTR = 0x401E0004 was exactly right (loopback bit 30 set), but MSR = 0x09 showed the controller stuck in init mode with the RX pin reading dominant. CAN only leaves init after 11 recessive bits on RX, and the unconnected PA11 was floating low. A pull-up on PA11 fixed it.
